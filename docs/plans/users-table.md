# Plan: users table

**Most likely reading of "add a users table":** move the users who can sign in out of configuration (`Auth:Users` plus user-secrets) into a `Users` table in Postgres, and make that table what login checks. User Ids stay the same, so every existing `Account.OwnerId` and `TransactionAuditLog.ActorUserId` value still points at the same person.
**Alternative reading (assumption A1):** create the table and keep configuration as the source of truth (a mirror or report table only). This plan does not do that.

---

## 0. What exists today (read from the code, commit `da4a773`)

There is **no users table, and no part of one**. Users are represented like this:

| Where | What |
|---|---|
| `src/Paysys.Api/appsettings.json` | `Auth:Users` holds one committed entry: `admin`, role `admin`, Id `54887bf0-35a4-4608-b365-d2ea2b0ca58d`. No `user`-role entry is committed |
| user-secrets (`UserSecretsId 923f2ff7-...`) | `Auth:Users:<n>:PasswordHash`, and possibly more entries (demo/guest). Their contents were not read for this plan |
| `src/Paysys.Api/Auth/AuthOptions.cs` | `DemoUser { Id, Username, Role, PasswordHash }`, bound from `Auth` |
| `src/Paysys.Api/Auth/AuthServiceCollectionExtensions.cs` | At startup it checks for at least one user, an Id, a Username, a valid Role, a PasswordHash, and no duplicate usernames or Ids. It fails startup otherwise. In Development a missing hash is replaced by a hash of the fixed password `"password"` |
| `src/Paysys.Api/Auth/UserAuthenticator.cs` | Singleton. Searches the in-memory list (case-insensitive, **not** trimmed) and checks the password with `PasswordHasher<DemoUser>`. An unknown user is checked against a dummy hash so timing does not reveal which usernames exist |
| `src/Paysys.Api/Auth/LoginThrottle.cs` | Singleton, in memory. Keyed on `Trim().ToLowerInvariant()` cut to 64 characters. Does not depend on where users are stored |
| `src/Paysys.Api/Auth/TokenService.cs` | `Issue(DemoUser)` puts `sub` (Id), `name` and `role` into the JWT |
| `src/Paysys.Api/Seeding/DemoSeeder.cs` | Reads `AuthOptions.Users` to choose the owners of the demo accounts |
| `PaysysDbContext` | `Account.OwnerId` and `TransactionAuditLog.ActorUserId` are plain GUIDs with no foreign key, and the comments say "there is no users table" |

The "3 user-secrets" that make the API fail closed are `ConnectionStrings:Paysys`, `Jwt:SigningKey` (32 characters minimum) and `Auth:Users:<n>:PasswordHash`. The last one is not required in Development because of the `"password"` fallback.

## 1. Goal

Store users in a Postgres `Users` table and make login check that table, with the same Ids, password hash format, JWT contents and lockout behaviour as today. Existing data stays valid without being rewritten.

## 3. Order of work

1. **Entity.** Create `User.cs` with its constructor checks. Build.
2. **Model.** Add `DbSet<User>` and its configuration to `PaysysDbContext`, and fix the comments on `OwnerId` and `ActorUserId`. Build.
3. **Migration.** Run `dotnet ef migrations add AddUsers --project src/Paysys.DAL`. Read the generated `Up`/`Down` and confirm they only create or drop `Users`, the index and the check constraint. If anything else is in it, stop and report. **Do not run `database update` against Neon** (step 11).
4. **Schema tests.** Write `UserTableTests.cs` and run it with `PAYSYS_TEST_PG`.
5. **Comment-only edits.** `TransactionAuditLog.cs` and `AuthOptions.cs`. Run `AuditChainTests` again to confirm the hash did not change.
6. **Authenticator and token.** Change `UserAuthenticator` (scoped, DB lookup, static dummy hash) and `TokenService.Issue(User)`. Write `UserAuthenticatorTests.cs`.
7. **Endpoint and DI.** Make the `AuthEndpoints` handler async, and change the registrations and checks in `AuthServiceCollectionExtensions`. Build. Confirm `LoginThrottleTests` still pass without changes.
8. **Importer.** Create `ConfigUserImporter.cs` and write `ConfigUserImporterTests.cs`.
9. **CLI branch.** Add `--import-users` in `Program.cs`.
10. **Seeder and README.** Change `DemoSeeder` and update `README.md`.
11. **Live step, needs the user's go-ahead for each command.** Against Neon: `dotnet ef database update`, then `dotnet run --project src/Paysys.Api -- --import-users`, then run the orphan check below. Then sign in as each imported user, and confirm a bad password gives 401 and that 5 bad passwords lock the account.

    ```sql
    SELECT a."Id", a."OwnerId" FROM "Accounts" a
    LEFT JOIN "Users" u ON u."Id" = a."OwnerId"
    WHERE u."Id" IS NULL;
    ```

    Same query for `"TransactionAuditLogs"."ActorUserId"`, ignoring NULLs. Report any rows. **Do not "fix" them** (Q4).
12. **Dev server shutdown** after the live check: `taskkill /F /T /PID` for Api (and Web, if it was started), then confirm with `Get-Process`.

Each step is one unit. Steps 1-3 can be one commit, 5 its own, 6-7 one, 8-9 one, 10 one.

## 5. Assumptions

- **A1** The goal is to move user storage into the database, not just mirror it (see top).
- **A2** User Ids are copied from config unchanged. This is what keeps existing `OwnerId` and `ActorUserId` values valid without changing data, and it keeps the audit chain intact. The chain hashes `actor=<id>`, so changing an Id would break verification.
- **A3** Password hashes are copied **as stored**: ASP.NET Core Identity `PasswordHasher` V3 format (PBKDF2, version marker, salt and iteration count inside the string). No rehashing, and the plaintext is never seen. When verification returns `SuccessRehashNeeded`, the login succeeds without rehashing, as it does today.
- **A4** Any demo or guest users are additional `Auth:Users` entries in local user-secrets or environment variables. The importer takes whatever the bound config contains. Their contents were not read.
- **A5** The table is filled by an explicit `--import-users` command, not by startup and not by migration `HasData`. Hashes are secrets and must not appear in a committed migration. A sync on every startup would quietly undo changes made in the database later.
- **A6** **No FK from `Accounts.OwnerId` to `Users.Id` in this change.** The migration runs before the import, so on Neon the table is empty when it is applied, and an FK would fail on the existing rows. A later migration can add it once the orphan check shows no rows (Q4).
- **A7** **`TransactionAuditLog.ActorUserId` never gets an FK.** The audit log must not depend on, or block, later changes to users, and historical rows can be NULL.
- **A8** The `PasswordHasher<TUser>` type parameter does not affect the hash. The default implementation ignores the user object. T4 checks this.
- **A9** Username matching stays case-insensitive and untrimmed, as today. `NormalizedUsername` uses `ToLowerInvariant()`. Usernames are assumed to be ASCII in practice, where this matches today's `OrdinalIgnoreCase`.
- **A10** The 64-character username limit matches `LoginThrottle.MaxKeyLength`, so two different usernames can never share one throttle bucket through truncation.
- **A11** After this change the API starts with **no** `Auth:Users` config. Fail-closed now means "no row in `Users`, no sign-in" (always 401), rather than "no config, no startup". `Jwt:SigningKey` and `ConnectionStrings:Paysys` stay required at startup.
- **A12** The Development `"password"` fallback is removed rather than moved into the importer (Q2).
- **A13** Importing users is **not** written to the audit hash chain in this change (Q3). The importer writes to the console only.
- **A14** Tests are written even though session memory says "skip unit tests at MVP stage". The repository now has a PG-backed test harness and a CI job that runs it, which suggests that preference has changed. Q6 confirms this.
- **A15** The implementer has `ConnectionStrings:Paysys` in local user-secrets, because `DesignTimeDbContextFactory` throws without it even for `migrations add`.

## 6. Risks and failure modes (authentication)

- **R1 Lockout order.** If the async rewrite moves `GetLockRemaining` after the DB lookup, a locked username costs a DB round trip and a PBKDF2 run, which brings back the CPU and DB cost the comment says is avoided. Throttle checks must come before any `await`. Review checks this line by line.
- **R2 Username enumeration by timing.** With DB lookups, a known user means one query plus a real hash check, and an unknown user means one query plus a dummy check. That stays balanced only if the dummy path still runs a full PBKDF2 check. If the dummy hash is computed lazily on the first unknown-user request, that first request is measurably slower. Compute it at type initialization (eager `Lazy` value, or a static field initializer).
- **R3 A known password stored in the database.** If the `"password"` fallback were kept and applied during import, every fresh clone's Neon database would hold users whose password is `password`, and those rows would outlive the Development environment. That is why the fallback is removed (A12, Q2).
- **R4 Nobody can sign in after deploy.** If the migration is applied but `--import-users` is not run, every login returns 401, including admin. This fails closed but is an outage. Mitigation: README order and step 11. Optional: a startup Warning log when `Users` is empty (not planned, Q5).
- **R5 Database unavailable during login.** The lookup throws, the global handler returns 500 with a trace id, and `RecordFailure` is **not** called. An attacker cannot use outages to get around lockout, because no 401 is returned. But a DB outage now blocks login, where before it only blocked data endpoints. A Neon cold start adds latency to the first login, equally for known and unknown users.
- **R6 Partial import.** An import interrupted partway could leave some users in and others out. That is why it runs in one transaction (T7, T8).
- **R7 Id or username conflicts.** If config and the table disagree (the same Id with a different username), quietly choosing either one could give accounts to the wrong person. The importer stops instead (T8).
- **R8 Orphaned ownership.** Accounts whose `OwnerId` matches no imported user, for example a guest user removed from secrets earlier, become unusable by anyone except admins reading them. This is already true today. The orphan check in step 11 makes it visible. Admins can still read them; nobody can write to them.
- **R9 Admin Id drift.** The pre-OwnerId accounts are owned by `54887bf0-...`, which is `admin` in config, although the migration comment calls it "demo". If the user's secrets actually define a different admin Id, or a separate "demo" user with that Id, the import keeps whatever config says. The orphan check shows the result. Nothing is changed automatically.
- **R10 Tokens outlive users.** Tokens issued before a user is removed from the table stay valid for up to 30 minutes. There is no per-request user check. This is unchanged from config-based users but more noticeable now that rows can be deleted. Out of scope (Q5).
- **R11 Audit chain.** This change must not touch `ComputeHash`, `AppendAndSaveAsync` or the chain lock. The only edit in `TransactionAuditLog.cs` is a comment. T9 (audit chain) protects this.
- **R12 Hashes leaking through logs.** The importer and login logs must contain username and Id only. No hash, no password and no connection string in console or log output. This follows the existing logging rules.
- **R13 Scoped vs singleton.** If `UserAuthenticator` stays singleton while it takes a scoped `DbContext`, DI validation fails in Development, or a shared context is used across threads in production. It must be scoped.

## 7. Out of scope

- An FK from `Accounts.OwnerId` to `Users.Id` (a later migration, after the orphan check, Q4).
- Any API for registration, user CRUD, password change or reset, or an admin user screen. Any `Paysys.Web` change.
- Persisting lockout state in the database. `LoginThrottle` stays in memory and single-instance.
- Disabling or deactivating users (`IsActive`/`DisabledAt`), revoking tokens, or checking on each request that the user still exists.
- Rehashing on `SuccessRehashNeeded`.
- Audit-chain entries for sign-in, sign-in failure or user import (Q3).
- Updating `docs/architecture/05-definition/as-is.md` (a baseline tied to a commit). The drift listed in section 0 should be handled in a separate docs task.
- Removing `Auth:Users` from `appsettings.json` or from user-secrets. Removing the stray `obj`-only folders.

## Open questions

1. **Source of truth:** Should the `Users` table replace configuration as the source of truth for login, with config used only by the one-shot `--import-users` command? Or do you want config to stay authoritative and the table to be a copy?
2. **Development password fallback:** Today, in Development, a user with no `PasswordHash` gets the password `password`. Once users live in the database, should that fallback be removed (the plan's default: every imported user needs a real hash in user-secrets)? Or should the importer use it in Development only, accepting that the database will then hold users whose password is `password`?
3. **Audit chain:** Should importing users write an entry to the audit hash chain (for example `User.Imported`, no actor), or is a console log enough for now (the plan's default)?
4. **Foreign key on Account.OwnerId:** After the import and the orphan check, do you want a follow-up migration that adds a foreign key from `Accounts.OwnerId` to `Users.Id`? And if the check finds accounts whose owner is not in the table, what should happen to them: reassign them to admin, create placeholder users, or leave them as they are?
5. **Empty table and removed users:** Should the API log a startup warning when the `Users` table is empty, and should a removed user's still-valid token (up to 30 minutes) be rejected? Both are out of scope in this plan unless you say otherwise.
6. **Tests:** Your saved preference says to skip unit tests at MVP stage and verify against the real database instead, but the repository now has a Postgres test harness and a CI job that runs it. Should this change include the tests listed in section 4, or only the live check against Neon in step 11?
