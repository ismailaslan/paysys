# Security review: gateway and card status (23 Nov 2026)

Method: a read-only review agent read the gateway, the bank-side gateway code and the card status code, then I checked finding 1 against the code. Nothing was run; findings come from reading. Tests are added as each fix lands.

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | High | A replayed payment (same idempotency key) enqueues a new gateway event with a fresh id, so another pending request for the same amount can be marked completed | Fixed 23 Nov (`27cd37e`): the event id is the transaction id, so a replay is a duplicate; the gateway also refuses a transaction already applied to a request. Tested on the bank side (`GatewayEventTests`) and on the gateway against Postgres (`BankEventEndpointTests`: the same payment under a new event id is refused) |
| 2 | Medium | Event matching is by terminal, amount and currency only, newest request first; not tied to the issued payment code | Fixed 23 Nov (`80a2189`): the gateway's request id travels with the payment code, is held on the server for the payer who looked it up, comes back on the event, and only that request is completed. A payment with no reference completes nothing. No database change. Tested: the matching rule (`PaymentMatchingTests`) and the reference path on the bank side (`PaymentCodeReferenceTests`, `GatewayEventTests`); the full chain was run by hand after the change on 23 Nov 2026 (terminal request, payment code, payment with PIN, request shown Completed with its transaction reference); the two-same-amount-requests case was not run live, only tested on the matching rule |
| 3 | Medium | Event id recorded before the payment update, so a failure loses the completion | Fixed 23 Nov (`e51b61d`): the event id and the update are saved in one database transaction. Tested against Postgres (`BankEventEndpointTests`: with the update made to fail, the event is not recorded and a retry completes the payment) |
| 4 | Medium | Card status has no concurrency check, so a bank block can be overwritten, and unblock sets Active even on a card the owner paused | Fixed 23 Nov (`cf97e1e`): the status is saved by a conditional update in the audit transaction, and a stale change is refused with 409; an unblock now leaves the card Paused. Tested (`CardStatusConcurrencyTests`, `CardStatusTests`) |
| 5 | Low | Card status checked once at the start of a transfer, not again before the debit | Fixed 23 Nov (`2860197`): the card's row is locked and checked again inside the transaction that saves the debit; a card paused or blocked in the meantime rolls the payment back. Tested (`CardStatusDuringPaymentTests`: blocked, paused and unchanged card) |
| 6 | Low | Out-of-range `X-Timestamp` gives a 500 | Fixed 23 Nov (`60240a1`): out-of-range timestamps are refused. Tested (`SecretsTests`) |
| 7 | Low | One merchant can fill the 5000 ticket slots | Fixed 23 Nov (`60240a1`): at most 10 open tickets per account. Tested (`TicketStoreLimitTests`) |
| 8 | Low | No rate limits on terminal and bank paths; 30 MB body limit before authentication; payment-code cap gives a 500 | Fixed 23 Nov (`60240a1`, `2ea2d88`): 64 KB body limit on the gateway, at most 20 open payments per terminal (429), payment-code cap now gives 503, 60 requests a minute per terminal id and 600 for all terminals together on `/v1/payments` (429), and rows older than 30 days are deleted from `Payments` and `ProcessedEvents`. Tested: the rate limits (`TerminalRateLimitTests`), the 20-open cap and the cleanup against Postgres (`BankEventEndpointTests`, `RetentionTests`). The 64 KB limit: `BodyLimitTests` checks that the server is started with the 64 KB setting; the refusal itself (413) is Kestrel's behaviour and is not exercised, because the test server does not run Kestrel. The rate limit is per terminal id, not per address, because the host's proxy hides the client address; someone who knows a terminal id can use up its allowance |
| 9 | Low | Denied access to cards and gateway keys is not audited | Fixed 23 Nov (`802a8cb`): asking for another user's card, or another merchant's terminal key, still gets a 404, and an `AccessDenied.CardChange` or `AccessDenied.GatewayKey` entry is written (a card or terminal that does not exist writes nothing). Tested (`DeniedAccessAuditEndpointTests`) |
| 10 | Low | Card status changes audited by account, not card | Fixed 23 Nov (`60240a1`): the card id is recorded on card status entries. Tested (`DeniedAccessAuditEndpointTests` checks the card id on the denial entry; the status entries are checked in `CardStatusTests`) |
| 11 | Low | Five-terminal limit can be beaten by parallel requests | Fixed 23 Nov (`60240a1`, `2a36159`): the terminal used for currency and bank is chosen in a fixed order, and the five-terminal limit is counted again inside the save's transaction, which holds the audit chain lock. Tested (`TerminalLimitConcurrencyTests`: eight simultaneous requests give exactly four new terminals) |
| 12 | Info | Smaller notes: event status ignored, event id not scoped per bank, base URL scheme not checked, in-memory event queue drops oldest | Noted |

Found sound by reading: terminal key generation, storage and comparison; bank key and signature checks (constant time, 5-minute window, 8 KB cap); one-use stream tickets; ownership and role checks on card and gateway-key endpoints; card checks before any bank call.

Not reviewed: tokenization, JWT and login (covered by tests and the previous review), infrastructure and hosting settings, dependencies.
